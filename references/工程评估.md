# 工程评估

由 [SKILL.md](../SKILL.md) 的任务分流触发加载。通用快检、澄清、授权、最小变更及完成核验以主入口为准。工程任务按下列档位选择检查；非代码任务只采用适用的失败处理、安全或恢复条款，不按行数定档。通过/有风险/待确认/N/A 按证据判断，未知不视为缺陷或通过。

## 定档与选型

1. **定档**：按改动规模分档，后续评估深度与档位匹配（粗判即可；共享模块/隐性语义先按清单 2 轻查波及面，加载附录本身不升档）：
   - 小：预估 <50 行、单模块、不动 schema/依赖/核心路径 → 完成主入口快检与清单 1/2/8，其余默认 N/A；但清单自身前提命中时仍启用——新入口（含新增入参、定时任务、回调、消息消费）→ 清单 6，新增外部调用 → 清单 5
   - 中：多模块波及、新增依赖，或预估 ≥50 行 → + 选型快检 + 清单 3–7
   - 大：动核心路径/schema/公共契约，或含不可逆决策（含不可恢复的数据改写）→ 全量 9 项
   - 同一需求分多批提交的按累计规模定档，不因单批 <50 行降为小档；判据命中多档取高档，均未命中归中档
2. **实施方案选型快检**（5 问，小档可整体 N/A）：技术/工具候选按主入口处理，本项只评估实施路径。① 方向对因——解决的是根因还是症状？② 备选对比——无论方案是否列出备选，评估者都按三方向自构最简对照——「不做/延后」「最朴素实现」「复用既有属主/挂载点」，方案自列备选仅作参照，警惕把朴素实现刻意写丑；选它的理由是事实还是偏好？③ 投入产出——实现+维护成本与收益是否匹配？有没有成本差一个数量级的路线（自研 vs 现成方案）？④ 可逆性——选错代价多大、能否低成本掉头？不可逆决策需更充分论证。⑤ 契合度——与现有技术栈/架构约定是否一致？引入新范式的理由是否充分？
3. **按清单评估落地**：逐项评估（通过/有风险/待确认/N/A），输出仅展开有风险与待确认项及一句话理由；待确认指适用但证据不足，不等同已发现缺陷，是否暂缓沿用主入口「澄清与执行」的判据；每项评估深度随档位自适应（小改动一句话带过，核心路径重点展开）。

## 评估清单（9 项：范围 → 波及 → 结构 → 质量 → 验收 → 发布）

1. **方案匹配度**（范围）：按主入口的最小必要变更要求核对需求覆盖，无镀金、无遗漏。
2. **影响面与兼容性**（波及）：动哪些模块、波及谁、是否核心路径；是否破坏现有 API/数据格式/接口契约；涉及数据变更时，schema 迁移、历史数据兼容。触发式轻查（改动对象是公共模块/共享工具/被多处调用的属主接口时启用，未命中即跳过）：调用方清点以机械枚举为准（grep/codegraph 查引用），不凭印象；签名与返回结构不变但语义变（缓存、时序、默认值、副作用、错误分支）属隐性行为变更，逐调用方判是否依赖旧语义，依赖者计入波及面，交主入口「完成核验」抽验
3. **复用与依赖**（结构-不重复造轮子）：新功能优先复用现有模块（写新工具方法/组件前先搜现有实现）；同一逻辑重复到第 3 处时评估抽取，是否抽取看业务语义、共同变化和维护成本，独立变化的相似代码可保留；仅 2 处重复通常不值得抽；新增外部依赖（库、服务、中间件）必须证明值得，有无更轻替代。复用评估两问：①有无可调用的现成实现；②**该动作的统一挂载点/属主是谁**——优先扩充既有属主接口（如可选参数），优于在 N 个调用点新增散点调用；两问都无着落时才考虑新开实现
4. **复杂度控制**（结构-复杂度）：触发线索——资深工程师会觉得这过于复杂吗？该问仅用于触发审视，结论须落到下列可检验子项：
   - 新增复杂度是否为必要复杂度；有无为假想场景做抽象/配置/预留
   - 改动行数是否与需求成比例（小需求大改动是失控信号）
   - 拆分评估——功能/页面粒度：单个页面或功能项承载 ≥3 个互相独立的职责（如列表+表单+设置混装）；代码粒度参考线（按技术栈校准，非硬上限）：函数 >50~80 行、单文件 >300~500 行（前端含模板的组件取上限）、嵌套 >3~4 层、圈复杂度 >10；参考线按本次新增/改写代码计量，存量超标仅提示。数值是软的：达到任一参考线即触发拆分评估，评估≠必须拆；评估义务是硬的：超线未评估、或决定不拆却不给一句理由 → 本项判「有风险」。正当动机：可复用、可维护（职责单一、降低认知负担）、可测试性、变化频率分离；拆分有间接成本（文件数膨胀、入口变多的导航成本），不为拆而拆
   - 是否存在更简单的实现路径
   - 模块边界是否清晰：新功能不直接读写其他模块的数据/内部状态，必须通过公开接口交互；但解耦以当前需求为界，不为假想扩展做隔离
5. **可靠性与容错**（质量）：失败路径——多步写入中途失败是否留脏数据（事务边界或补偿）；边界条件——空值/极大值/非法输入/并发同改一条数据；幂等——重试/重复提交/消息重投场景必查；外部调用是否有超时/重试/降级
6. **安全**（质量）：新入口的鉴权、注入、敏感信息泄露风险
7. **性能**（质量）：明显隐患（N+1、循环内远程调用、大数据量退化）
8. **验证方式**（验收）：共同要求见主入口「完成核验」；调用方影响面来自清单 2。触发式补充两条（未命中即 N/A，不以工具配置或测试代码量作硬门槛）：① 动态构造代码——方案含运行时才解析/求值的代码（eval/new Function/exec、字符串拼 SQL/shell/正则、动态 import、模板中的动态代码）时，验收须复用或补充覆盖实际解析/执行路径的运行验证；已有适用的静态检查（lint/typecheck）时一并运行，缺少这类工具本身不阻塞——编译/构建通过不代表此类代码无语法错；② 测试规模参考——测试代码量与需求风险面显著失衡（过少漏关键风险 / 过多样板仪式）时轻度提醒一句，不设比例硬线
9. **上线保障**（发布）：能否回滚（含回滚后数据怎么办）；不可逆/核心路径的应对（回滚、数据迁移）须在正式实施前先演练验证——测试环境或数据副本上跑通一次，未验证的回滚视同没有；出错时日志能否定位问题；影响面大时才考虑灰度/开关

## 评估自身的复杂度

不适用项标 N/A，不强行挑刺；保留必要复杂度，明确指出过度设计。评审提出的新增断言、检查或层次须与风险和成本相称；近零成本的机械检查标注为 sanity，不升格为硬门禁。
