# 方案把关（vetting-plans）

对软件实现方案做把关评估的 Kimi Code 技能：在动手写代码之前，判断方案路径是否高效、可靠、复杂度可控，并顺带快检需求本身的合理性。

## 设计意图

### 定位

- 服务于**中小型项目**：砍掉大型分布式语境的检查项（单点故障、爆炸半径、灰度发布），保留中小项目高频踩坑点（数据迁移、新增依赖、行数膨胀、改后验收）
- 评估对象是**实现方案**，顺带快检需求；不是代码评审，不是需求评审
- 评估深度随改动规模自适应：小改动一句话带过，核心路径重点展开

### 把关，不是打分

技能的核心立场是 gatekeeper 而非评分员：

- 发现更简单的路径**必须明确提出异议**，而不是顺着方案评
- 复杂度超配必须指出，输出格式中"简化建议"是固定必填项
- 每条结论落到可执行的删减/修改建议，不打模糊的分数

### 防过度工程是主线

过度设计的拦截分布在多个环节，形成闭环：

- 需求快检：有没有更简单的满足方式
- 清单 1：无镀金、无顺带重构
- 清单 4：新增依赖必须证明值得
- 清单 6：必要复杂度、行数成比例、三次法则（重复到第 3 处才抽公共模块）、拆分不为拆而拆
- 输出：简化建议固定槽位

### 结构性约束优于文字提醒

遵循"遗漏元素 → 在输出模板中加必填槽位"的原则，而不是在附近加 prose 提醒。例如"改动规模预估"曾是评估时的思考点但输出中常丢失，后改为输出格式的固定必填项。

### 命名与语言

- `name` 用英文 `vetting-plans`：符合 agentskills.io 规范（`[a-z0-9-]`），跨运行时兼容，GitHub 可检索
- 正文用中文：技能服务于中文使用场景，中文指令引导更准
- description 中文触发词在前（高频自用），英文检索句垫底（GitHub 发现）

## 版本变更

### v2.0.0（2026-08-25）

- 更名：快速评估 → **方案把关**（GitHub 仓 `vetting-plans`），名实对齐：vetting = 把关
- description 末尾追加英文检索句，触发词同步更新

### v1.4.0（2026-08-25）

- 清单 7（验证方式）：新增改后验收两维度——① 正常显示/运行（无报错、无渲染问题、边界输入不崩）② 符合设计预期（对照需求逐条核对，不只走通主路径）

### v1.3.0（2026-08-25）

- 输出格式新增固定必填项：**改动规模预估**（粗估行数 + 是否成比例），修复"行数评估停留在思考层、输出常丢失"的问题

### v1.2.0（2026-08-25）

- 面向中小项目整体优化：
  - 工作流第 1 步：涉及现有代码时先核对现状再评，防空谈
  - 清单 2：并入数据迁移检查（schema、历史数据、回滚后数据）
  - 清单 4：高可用 → 外部依赖与容错，砍单点故障/爆炸半径，补新增依赖评估
  - 清单 6：重构为主句+子项；新增"行数膨胀是否该拆分"评估（可复用/可维护/可测试/变化频率分离 + 不为拆而拆）
  - 清单 8：措辞中小项目化，灰度降为"影响面大时才考虑"

### v1.1.0（2026-08-25）

- 清单 6 补充：改动行数与需求成比例检查；重复实现三次法则（复制到第 3 处抽公共模块，2 处不抽）

### v1.0.0

- 初版：工作流 3 步 + 评估清单 8 项 + 固定输出格式 + 原则
