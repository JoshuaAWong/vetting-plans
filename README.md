# 方案把关（vetting-plans）

对软件实现方案做把关评估的 Kimi Code 技能：在动手写代码之前，判断方案路径是否高效、可靠、复杂度可控，并顺带快检需求本身的合理性。

## 设计意图

### 定位

- 服务于**中小型项目**：砍掉大型分布式语境的检查项（单点故障、爆炸半径），灰度降级为影响面大时才考虑，保留中小项目高频踩坑点（数据迁移、新增依赖、行数膨胀、改后验收）
- 评估对象是**实现方案**，顺带快检需求；不是代码评审，不是需求评审
- 评估深度随改动规模自适应：小改动一句话带过，核心路径重点展开
- 风险应对须验证有效：普通风险在验收中真实触发一次（模拟触发即可），不可逆/核心路径在正式实施前演练——验证强度随档位分层，不为小改动加演练流程
- 默认自查：AI 出实现方案/plan 前默认先过本技能自查，不等用户点名；自查属同源评估，结论标注「自查（非独立把关）」，完整输出格式仅用户点名把关时展开

### 把关，不是打分

技能的核心立场是 gatekeeper 而非评分员：

- 发现更简单的路径**必须明确提出异议**，而不是顺着方案评
- 复杂度超配必须指出，输出格式中"简化建议"是固定必填项
- 每条结论落到可执行的删减/修改建议，不打模糊的分数

### 防过度工程是主线

过度设计的拦截分布在多个环节，形成闭环：

- 需求快检：有没有更简单的满足方式
- 清单 1：无镀金、无顺带重构
- 清单 3：新增依赖必须证明值得；三次法则（重复到第 3 处才抽公共模块）
- 清单 4：必要复杂度、行数成比例、拆分不为拆而拆
- 输出：清单结果与简化建议固定槽位

### 结构性约束优于文字提醒

遵循"遗漏元素 → 在输出模板中加必填槽位"的原则，而不是在附近加 prose 提醒。例如"改动规模预估"曾是评估时的思考点但输出中常丢失，后改为输出格式的固定必填项。

### 命名与语言

- `name` 用英文 `vetting-plans`：符合 agentskills.io 规范（`[a-z0-9-]`），跨运行时兼容，GitHub 可检索；本地工作区经 smudge 过滤器显示为 方案把关（见文末维护说明）
- 正文用中文：技能服务于中文使用场景，中文指令引导更准
- description 中文触发词在前（高频自用），英文检索句垫底（GitHub 发现）

### v2.8.1（2026-10-13）

- 清单 2 新增触发式轻查：改动对象是公共模块/共享工具/被多处调用的属主接口时启用——调用方清点以机械枚举为准（grep/codegraph 查引用），不凭印象；点名隐性行为变更（签名与返回结构不变但语义变：缓存、时序、默认值、副作用、错误分支），逐调用方判是否依赖旧语义，依赖者计入波及面交清单 8② 抽验。依据：此类改动最阴的形态是「契约字面未破坏」，清单 2 原表述易顺口判通过；且清单 8② 的抽验范围继承清单 2 的识别结果，上游漏数下游全漏（观复量化 v2.94.3 raceRtkBudget 实例：签名不变行为变，靠逐调用方核对收口）。版本号沿 v2.2.1 先例（单子项新增走 patch）

### v2.8.0（2026-10-13）

- 清单 8 新增两条触发式轻查（未命中即 N/A，不做硬性限制）：⑤ 动态构造代码——方案含运行时才解析/求值的代码（eval/new Function/exec、字符串拼 SQL/shell/正则、动态 import、模板渲染）时，验收须含静态检查（lint/typecheck）+ 覆盖该路径的运行时冒烟，堵「编译/构建通过但运行时才爆语法错」的检查空档；⑥ 测试规模参考——测试代码量与需求风险面显著失衡（过少漏关键风险 / 过多样板仪式）时轻度提醒一句，不设比例硬线

## 维护说明

本地目录即 git 仓库，直连 GitHub。通过 clean/smudge 过滤器实现：仓库存 `name: vetting-plans`，本地工作区显示 `name: 方案把关`，换名全自动。

日常流程：改完 `git add -A && git commit && git push` 即可。

换机器 clone 后需重配过滤器（配置存在本地 `.git/config`，不随仓库走）：

```bash
git config filter.vp.clean "sed 's/^name: 方案把关$/name: vetting-plans/'"
git config filter.vp.smudge "sed 's/^name: vetting-plans$/name: 方案把关/'"
git checkout -f main  # 重新检出以应用 smudge
```
