# 方案把关（vetting-plans）

对软件实现方案做把关评估的 Kimi Code 技能：在动手写代码之前，判断方案路径是否高效、可靠、复杂度可控，并顺带快检需求本身的合理性。

## 设计意图

### 定位

- 服务于**中小型项目**：砍掉大型分布式语境的检查项（单点故障、爆炸半径、灰度发布），保留中小项目高频踩坑点（数据迁移、新增依赖、行数膨胀、改后验收）
- 评估对象是**实现方案**，顺带快检需求；不是代码评审，不是需求评审
- 评估深度随改动规模自适应：小改动一句话带过，核心路径重点展开

### 把关，不是打分

技能的核心立场是 gatekeeper 而非评分员：

- 发现更简单的路径**必须明确提出异议**，而不是顺着方案评
- 复杂度超配必须指出，输出格式中"简化建议"是固定必填项
- 每条结论落到可执行的删减/修改建议，不打模糊的分数

### 防过度工程是主线

过度设计的拦截分布在多个环节，形成闭环：

- 需求快检：有没有更简单的满足方式
- 清单 1：无镀金、无顺带重构
- 清单 4：新增依赖必须证明值得
- 清单 6：必要复杂度、行数成比例、三次法则（重复到第 3 处才抽公共模块）、拆分不为拆而拆
- 输出：简化建议固定槽位

### 结构性约束优于文字提醒

遵循"遗漏元素 → 在输出模板中加必填槽位"的原则，而不是在附近加 prose 提醒。例如"改动规模预估"曾是评估时的思考点但输出中常丢失，后改为输出格式的固定必填项。

### 命名与语言

- `name` 用英文 `vetting-plans`：符合 agentskills.io 规范（`[a-z0-9-]`），跨运行时兼容，GitHub 可检索
- 正文用中文：技能服务于中文使用场景，中文指令引导更准
- description 中文触发词在前（高频自用），英文检索句垫底（GitHub 发现）

## 版本变更

### v2.2.1（2026-08-27）

- 清单 4 新增子项：模块边界是否清晰——新功能不直接读写其他模块的数据/内部状态，须通过公开接口交互；反向约束：解耦以当前需求为界，不为假想扩展做隔离（防过度解耦）

### v2.2.0（2026-08-27）

- 清单结构性重组：8 项 → 9 项，排序改为 范围 → 波及 → 结构 → 质量 → 验收 → 发布
- 消除 5 处职责交叉：
  - 复用/抽取三处分散 → 收敛为新清单 3「复用与依赖」（内部复用 + 三次法则 + 外部依赖，"不重复造轮子"单一职责）
  - 失败/边界三处分散 → 设计归清单 5、验收归清单 8
  - 清单 3「可靠性与安全」拆分：可靠性+容错 → 清单 5，安全独立 → 清单 6
  - 回滚两处分散 → 统一归清单 9
  - 容错（超时/重试/降级）从原清单 4 并入清单 5，"失败怎么办"单一归属
- 使用示例的清单引用编号同步更新

### v2.1.0（2026-08-27）

- 工作流新增第 3 步**方案选型快检**（5 问，小改动可整体 N/A）：方向对因、备选对比、投入产出、可逆性、契合度
- 形成三层定位：需求快检（做不做）→ 选型快检（走哪条路）→ 清单 8 项（路怎么铺）
- 采用轻量快检而非第二套清单：避免小改动也要过重清单，保持评估深度自适应

### v2.0.0（2026-08-25）

## 维护说明

本地目录即 git 仓库，直连 GitHub。通过 clean/smudge 过滤器实现：仓库存 `name: vetting-plans`，本地工作区显示 `name: 方案把关`，换名全自动。

日常流程：改完 `git add -A && git commit && git push` 即可。

换机器 clone 后需重配过滤器（配置存在本地 `.git/config`，不随仓库走）：

```bash
git config filter.vp.clean "sed 's/^name: 方案把关$/name: vetting-plans/'"
git config filter.vp.smudge "sed 's/^name: vetting-plans$/name: 方案把关/'"
git checkout -f main  # 重新检出以应用 smudge
```
